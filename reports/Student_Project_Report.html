1. Architecture Overview

The solution connects two isolated VPCs using an AWS VPC Peering connection with strict non-overlapping CIDRs and minimal least-privilege security group rules.

  • VPC A (10.10.0.0/16): Contains a public subnet with an Internet Gateway and Bastion host (10.10.1.10), plus a private subnet with ewb-app-a (10.10.2.10).
  • VPC B (10.20.0.0/16): Contains a private subnet with ewb-app-b (10.20.1.10) and no internet gateway.
  • Administration: Managed from local laptop using SSH ProxyJump via ewb-bastion.

5. Architecture Defense & Viva Answers

1. Why is the return route needed?

Network routing is directional. When App-A sends a packet to App-B, it reaches App-B through the peering link. When App-B replies, its routing engine consults its own route table. If no route exists for 10.10.0.0/16 pointing back to the peering connection, the packet cannot leave VPC B.

2. Why is the App-B SSH source the bastion private IP?

Using SSH ProxyJump, the bastion acts as an application-level proxy. The bastion terminates the first TCP leg and initiates a brand new TCP connection to App-B using its own private IP (10.10.1.10). Therefore, App-B's firewall sees the source as 10.10.1.10, not your laptop's public IP.

3. Why does Active peering not guarantee a successful ping?

Peering only establishes the network pipeline. Communication requires four aligned components: Active peering status, correct route table targets in both VPCs, explicit security group ingress rules, and permissive Network ACLs.

4. Can VPC B use VPC A's internet gateway over peering?

No. AWS VPC peering is strictly non-transitive. It does not support edge-to-edge routing, meaning traffic from one peered VPC cannot traverse another VPC to access an Internet Gateway, NAT Gateway, or VPN.
